2. Product Vision
Nexus Pathways AI is a secure, multi-tenant correctional education platform designed to support county jails, juvenile 
justice programs, state Departments of Corrections, federal correctional settings, adult education programs, and reentry 
organizations. The system is designed to support education from intake through release while remaining usable in 
restrictive institutional technology environments.

4. Non-Negotiable Product Rules

One codebase must support a small county jail and a statewide correctional system.

Every new feature must respect tenant and facility boundaries at both UI and API levels.

Sensitive disability/special-education records require additional permissions and audit logging.

5. Phased Replit Development Roadmap
Phase 0 - Product Governance & Documentation
Goal: Create the permanent rules Replit must follow before feature development begins.

Create /docs with PRODUCT_VISION.md, PRODUCT_REQUIREMENTS.md, SECURITY_REQUIREMENTS.md, 
ACCESSIBILITY_REQUIREMENTS.md, DATA_CLASSIFICATION.md, USER_ROLES.md, DATABASE_RULES.md, 
AI_SAFETY_RULES.md, DEPLOYMENT_REQUIREMENTS.md, and CODING_STANDARDS.md.

Define feature flags for ABE, HSE, Special Education, Accessibility, AI Tutor, Career, Reentry, Passport, and Offline 
Mode.

Define data sensitivity levels and which roles can access each class of data.
Exit gate
All governing documents exist, are internally consistent, and Agent confirms that later work will follow them.
Phase 1 - Foundation, Authentication & Multi-Tenancy
Goal: Create the secure skeleton of the national platform.

Create the monorepo/application structure, PostgreSQL database, typed ORM, environment configuration, and 
Docker-compatible setup.

Implement Organization → Agency → Region → Facility → Program → Cohort hierarchy.

Implement secure authentication, role-based access control, granular permissions, session controls, and audit-event 
framework.

Seed one Escambia County Corrections demo tenant with synthetic data only.

Create simple authenticated Learner, Educator, and Administrator shells.
Exit gate
Automated tests prove authentication, tenant isolation, facility isolation, role restrictions, and audit-event generation.
Phase 2 - National Organizational Model
Goal: Make the same system usable by counties, states, and federal organizations.

Complete the organizational hierarchy and scoped administrator views.

Allow agency administrators to manage facilities and programs beneath their scope.

Prevent facility users from traversing URLs or APIs into another facility or tenant.

Create configuration management for tenant-specific modules and policy settings.
Exit gate
A state-level demo administrator can see multiple facilities, while a facility administrator can see only the assigned 
facility.

Phase 3 - Pathways Learn™
Goal: Build the secure learner experience.

Create learner home page, assigned coursework, progress, learning goals, instructional hours, approved resources, 
and accessibility toolbar.

Keep navigation simple and suitable for desktop/tablet use in institutional environments.

Block direct messages, social features, unrestricted URLs, arbitrary file uploads, and unauthorized external 
communication.

Add session timeout and configurable inactivity controls.
Exit gate
A learner can log in, complete assigned demo content, and never access educator/admin functions or another learner 
account.
Phase 4 - Curriculum Management Engine
Goal: Create a configurable content system rather than hardcoded lessons.

Implement Course → Subject → Module → Unit → Lesson → Activity → Assessment → Skill structure.

Support ABE 1-6, HSE preparation, literacy, ESL, digital literacy, financial literacy, workforce, and reentry categories.

Create staff-authoring workflows for lessons and versioned content publishing.

Add content status: Draft, Review, Approved, Published, Retired.
Exit gate
Authorized staff can create and publish a sample course without code changes; learners only see approved content.
Phase 5 - Pathways Assess™
Goal: Build placement, diagnostic, mastery, and practice assessment capability.

Implement placement, diagnostic, lesson quiz, unit assessment, post-assessment, and practice assessment types.

Create structured question metadata: subject, domain, skill, learning objective, difficulty, level, question type, 
explanation, and remediation lesson.

Add attempt history, scoring, mastery updates, and educator review.

Separate internally created practice assessments from official/licensed exams.
Exit gate
Scores are reproducible, mastery calculations are tested, and question access is protected from unauthorized users.
Phase 6 - Adaptive Learning Engine
Goal: Turn assessment evidence into individualized instruction.

Calculate skill mastery by learner and subject.

Identify persistent skill gaps and generate prioritized learning recommendations.

Generate an Individual Learning Plan with staff override capability.

Advance or remediate learners based on configurable mastery thresholds.

Retain recommendation history so staff can understand why assignments were made.
Exit gate
Given known synthetic assessment results, the engine produces the expected learning plan and recommendations.

Phase 7 - Pathways Access™
Goal: Integrate accessibility and applicable disability/special-education workflows.

Create AccessibilityProfile, Accommodation, AccommodationAssignment, IEP, IEPGoal, IEPProgress, IEPService, 
Evaluation, TransitionPlan, RelatedService, ServiceDeliveryLog, AssistiveTechnology, AccommodationApproval, and 
AccessibilityAuditLog models.

Support adult accommodation plans separately from IEP workflows.

Implement text-to-speech hooks, keyboard navigation, text scaling, high contrast, spacing controls, 
captions/transcripts, focus mode, reduced-distraction mode, and step-by-step/simplified instructional modes.

Add special-education coordinator dashboard with due-date reminders and progress monitoring.

Restrict disability/special-education records with dedicated permissions.
Exit gate
Accessibility workflows function without exposing diagnosis/documentation to roles that only need to know the 
approved instructional support.
Phase 8 - Adaptive Accessibility
Goal: Make instructional presentation respond to approved supports.

Allow authorized staff to set learner accessibility preferences and accommodations.

Expose learner controls only where policy permits.

Add “Read Aloud,” “Simplify,” “Break Into Steps,” “Define This Word,” “Show an Example,” “Practice With Me,” and 
“Focus Mode” interfaces.

Ensure standard content remains usable when optional assistive services are unavailable.
Exit gate
A learner with an assigned accessibility profile receives the configured presentation supports without changing 
another learner’s experience.
Phase 9 - Pathways Tutor AI™
Goal: Add an optional, closed-domain educational tutor.

Ground AI responses in approved curriculum and learner-authorized academic context.

Allow explanations, hints, examples, practice, simplification, and approved translation assistance.

Block unrestricted web access, external communication, security-sensitive assistance, disability diagnosis, 
accommodation approval, and unilateral IEP modification.

Create agency-level and tenant-level kill switches for AI.

Log AI interactions according to policy and minimize exposure of sensitive records.
Exit gate
Red-team tests show the tutor refuses prohibited requests and still supports approved educational help. Core product 
works with ENABLE_AI_TUTOR=false.
Phase 10 - Pathways Educator™
Goal: Give instructors actionable academic workflows.

Build cohort rosters, assignment management, diagnostics, mastery views, interventions, instructional-hour tracking, 
approved accommodation views, and progress reporting.

Allow educators to create and revise learning plans within assigned scope.

Create alerts for learners needing intervention or reassessment.

Ensure educators only see special-education information required for their role.

Goal: Create pre-release readiness planning.

Create configurable reentry domains such as education, employment, identification, housing planning, transportation,

Phase 14 - Pathways Passport™
Goal: Preserve permitted achievements after release.

Create a controlled transition from restricted institutional identity to a civilian account where permitted.



Do not automatically transfer disability, medical, security, or other sensitive correctional information.

Require explicit policy/consent workflows for any protected transfer.
Exit gate
The transfer test demonstrates an allow-list model: only approved fields are copied to the civilian profile.

Phase 15 - Government-Grade Reporting
Goal: Create auditable operational and outcome reports.

Phase 16 - Pathways Connect™
Goal: Create the integration layer needed for national adoption.

Design versioned REST APIs and webhook architecture.

Prepare integration adapters for SAML/OIDC SSO, SCIM, CSV, secure file transfer, SCORM, xAPI, and LTI where


Keep vendor-specific connectors separate from the core domain model.

Document integration contracts and authentication methods.
Exit gate
A documented sandbox API can exchange non-sensitive synthetic learner/course data without bypassing 
authorization rules.
Phase 17 - Cloud, Private & Edge Deployment
Goal: Make restrictive correctional deployments realistic.

Package application services for container deployment.

Support Pathways Cloud, dedicated/private environment, and Pathways Edge on a facility LAN.

Design local authentication/content/database operation for approved no-public-internet deployments.

Create controlled content/software update workflow, backup process, and recovery procedure.
Exit gate
A test environment operates through the defined local-network mode without learner public internet access.
Phase 18 - Security Hardening
Goal: Stop feature work and perform a dedicated security pass.

Test authentication, MFA architecture, session controls, password reset, rate limits, authorization, IDOR, cross-tenant 
access, XSS, CSRF, injection, file handling, secrets, exports, APIs, and backups.

Test every high-privilege role and sensitive record route.

Add automated security regression tests for issues discovered.

Document unresolved risks instead of hiding them.
Exit gate
No known critical/high authorization or tenant-isolation defect remains open for the demo release.

12. Permanent Replit Project Instruction
NEXUS PATHWAYS DEVELOPMENT RULE
Never implement a new major feature without:
1. Checking tenant isolation.
2. Checking role-based authorization.
3. Adding audit events where applicable.
4. Adding automated tests.
5. Updating documentation.
6. Checking accessibility implications.
7. Checking offline/restricted-network implications.
8. Checking whether sensitive data is involved.
Never claim the product is:
- CJIS compliant
- FERPA compliant
- HIPAA compliant
- SOC 2 certified
- FedRAMP authorized
- Section 508 compliant
- ADA compliant
- IDEA compliant
unless authorized human review and supporting evidence establish that claim.
The application may instead state that it is designed to support applicable requirements.
